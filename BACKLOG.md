# Идеи для развития mail2tg

Идеи записаны в порядке приоритета. Статус реализации указан в соответствующих пунктах.

## 1. Разделить успешную доставку и пропуск из-за ошибки

Статус: реализовано локально. Проверяются ответы `select/search/fetch`,
неудачные UID сохраняются отдельно для новых писем и каждой даты истории.
После пяти неудачных попыток запись остаётся для ручного повтора через
`retry_uids`. Добавлены проверки с имитацией IMAP и ошибок доставки.
Уведомления владельцу и прогресс отдельных частей письма — следующие этапы.

Сейчас после большинства исключений `last_uid` продвигается. Это происходит и при отсутствии полученного тела письма: письмо может остаться непересланным без автоматического повтора.

Что сделать:

- Проверять результаты IMAP-команд `select`, `search` и `fetch`.
- Хранить неудачные UID, число попыток и причину ошибки без содержимого письма.
- Повторять обработку временных ошибок, а окончательно пропущенные письма учитывать отдельно.
- Не позволять одному проблемному письму блокировать остальные.

Критерий готовности: временная ошибка не приводит к незаметной потере письма; неудачные письма можно найти и повторно обработать.

## 2. Сохранять прогресс отправки внутри письма

Статус: реализовано локально. Подтверждённые части текста, ID первого сообщения,
вложения и этап скриншота сохраняются между попытками. Добавлены тесты сбоев
после частичной доставки и резервный артефакт состояния при ошибке push.
Ограничения при неоднозначном ответе Telegram и потере локального состояния
сохраняются; подробности восстановления описаны в README.

Если текст уже опубликован, а отправка вложения оборвалась из-за сети, следующий запуск начинает письмо заново и может создавать дубли.

Что сделать:

- Сохранять ID первого Telegram-сообщения и завершённые этапы отправки.
- Учитывать отправленные части текста, вложения и скриншоты.
- При повторном запуске продолжать с незавершённого этапа.
- Предусмотреть восстановление после неудачного сохранения состояния в репозиторий.

Критерий готовности: после сбоя между этапами уже подтверждённые этапы не отправляются повторно, а оставшиеся продолжаются с привязкой к первому сообщению.

Ограничение: при сетевом таймауте Telegram мог принять запрос без получения ответа клиентом. Полностью исключить такие дубли одним локальным журналом нельзя.

## 3. Изолировать внешние ресурсы при создании скриншотов

JavaScript в браузере уже отключён, но исходный HTML может загружать внешние изображения, CSS и другие ресурсы. Это активирует почтовые трекеры и делает рендеринг зависимым от сторонних серверов.

Что сделать:

- По умолчанию блокировать внешние сетевые запросы при рендеринге.
- Сохранить поддержку встроенных в письмо изображений `cid:` через подстановку данных.
- Ограничить размеры страницы и потребление ресурсов до создания полного скриншота.
- При необходимости предусмотреть явную настройку загрузки внешних ресурсов.

Критерий готовности: по умолчанию скриншот создаётся без внешних запросов, встроенные изображения сохраняются, чрезмерно большая страница обрабатывается с установленными ограничениями.

## 4. Добавить тесты преобразования писем и сценариев сбоев

Собственный HTML-парсер — самая сложная часть проекта. Тесты цикла доставки,
истории и очередей ошибок уже добавлены; проверки парсера и запуск тестов в CI ещё нужны.

Что сделать:

- Подготовить обезличенные примеры писем Outlook и Gmail, вложенных таблиц, повреждённого HTML, длинных строк и MIME-вложений.
- Проверять сохранение текста, корректность разметки и разбиение на сообщения.
- Проверять частичную отправку, повторные попытки и ошибки IMAP с подменой сетевых вызовов.
- Запускать тесты в GitHub Actions.

Критерий готовности: основные варианты писем и сценарии ошибок проверяются автоматически без доступа к настоящей почте и Telegram.

## 5. Сделать установку и сопровождение воспроизводимыми

Зависимости устанавливаются без фиксации версий, конфигурация читается при импорте, а вся логика находится в одном скрипте. README содержит только краткое описание.

Что сделать:

- Зафиксировать версии зависимостей и описать их обновление.
- Вынести загрузку и проверку настроек в отдельную функцию, чтобы импорт не требовал секретов.
- Постепенно разделить код на модули: конфигурация, состояние, IMAP, преобразование писем, Telegram и скриншоты.
- Расширить README: настройка секретов, локальный запуск, первый запуск, пересылка истории и восстановление после сбоев.

Критерий готовности: проект можно установить и запустить по документации с определёнными версиями зависимостей, а модули можно импортировать для тестирования без секретов и сетевых подключений.
