# mail2tg

Пересылка писем из Яндекс Почты в Telegram-канал через GitHub Actions.
Бот публикует текст, вложения и скриншоты HTML-писем. Доступ к почте — только
для чтения: письма не удаляются и не помечаются прочитанными.

## Структура проекта

```text
.
├── .github/workflows/
│   ├── mail2tg.yml           # Запуск бота, сохранение состояния, уведомления
│   └── tests.yml             # Автоматические тесты и проверка браузера
├── tests/                   # Доставка, история, состояние, мониторинг, скриншоты
├── mail2tg.py               # IMAP, преобразование писем и отправка в Telegram
├── monitoring.py            # Уведомления владельцу и внешний мониторинг
├── state.json               # Позиции обработки, очереди ошибок и прогресс
├── requirements.txt         # Версии прямых зависимостей
├── BACKLOG.md               # Статусы и планы развития
└── README.md
```

## Настройка

Окружение GitHub Actions: **Python 3.12, Ubuntu 24.04**.
Добавьте секреты в **Settings → Secrets and variables → Actions**:

| Секрет | Назначение |
| --- | --- |
| `IMAP_USER` | Адрес почтового ящика |
| `IMAP_PASSWORD` | Пароль приложения Яндекса |
| `TG_TOKEN` | Токен Telegram-бота |
| `TG_CHAT_ID` | ID или `@username` канала |
| `TG_ADMIN_CHAT_ID` | Необязательно: ID чата владельца для уведомлений |
| `HEALTHCHECK_URL` | Необязательно: Ping URL внешнего мониторинга |

Боту нужны права публикации в канале. Для личных уведомлений владелец должен
открыть чат с ботом и нажать **Start**.

По умолчанию используются `imap.yandex.ru`, папка `INBOX`, часовой пояс
`Europe/Samara`, лимит 20 писем и скриншоты всех HTML-писем. Изменения настроек
передаются через окружение [workflow](.github/workflows/mail2tg.yml).
Первый обычный запуск сохраняет текущую позицию и пропускает старые письма.

## Запуск

### Вручную

**Actions → Почта → Telegram → Run workflow**:

| Параметр | Назначение |
| --- | --- |
| `since` | Пусто — новые письма; `2026-09-01` или `01.09.2026` — обработанная история с этой даты |
| `max_per_run` | Лимит писем и повторных попыток; по умолчанию 20 |
| `restart_history` | Намеренно повторить историю с начала; требуется `since` |
| `retry_uids` | Сбросить счётчики ошибок указанных UID, например `19,21` |
| `test_notification` | Только тест личного уведомления; остальные параметры игнорируются |

История имеет отдельную позицию и фиксированную верхнюю границу. Повторный
запуск с той же датой продолжает следующую порцию; после завершения ничего
не отправляет. Для повтора включите `restart_history`, а для следующей порции
снимите его. Позиция новых писем и их очереди не меняются.

### По расписанию

Используется cron-job.org с интервалом **5 минут**. Встроенное расписание GitHub
также сохранено, но не гарантирует точного времени запуска.

В cron-job.org настройте **POST** на адрес:

```text
https://api.github.com/repos/dmitrii-a-piskunov/mail2tg/actions/workflows/mail2tg.yml/dispatches
```

Заголовки:

```text
Authorization: Bearer <GITHUB_TOKEN>
Accept: application/vnd.github+json
Content-Type: application/json
X-GitHub-Api-Version: 2026-03-10
```

Тело запроса:

```json
{"ref":"main","inputs":{"since":"","max_per_run":"20"}}
```

Токен — fine-grained, только для этого репозитория, с правом **Actions: Read and write**.
Храните его в cron-job.org и заменяйте после истечения срока.
В автоматическом запуске `since` и `retry_uids` должны быть пустыми,
`restart_history` и `test_notification` — выключены.

## Надёжность

Прогресс сохраняется в `state.json`: позиция новых писем, история, ошибки
и подтверждённые этапы отправки. После сбоя бот продолжает незавершённые этапы.
После пяти неудачных попыток письмо остаётся для ручного повтора через
`retry_uids`; для истории также требуется её дата `since`.

Ошибки отдельных писем видны в логах и очередях, но не делают весь workflow
неуспешным. Ошибки IMAP-папки, поиска и сохранения состояния останавливают запуск.
Повреждённый или отсутствующий `state.json` не сбрасывается автоматически.
При смене IMAP `UIDVALIDITY` позиции и очереди инициализируются заново.

Если push состояния не удался, приостановите расписание и восстановите прогресс
из актуальной истории Git или артефакта `mail2tg-state-<ID запуска>` в Actions.
Артефакт хранится 7 дней, если его загрузка удалась. Перед возобновлением
сверьте состояние: новая копия не должна заменяться старой. `{}` означает
намеренный сброс, а не восстановление.

Дубли возможны при потере ответа Telegram или состояния до push. Изменение
плана частичной доставки вызывает `DeliveryPlanChanged` и требует ручного разбора.

## Мониторинг

Владелец получает уведомления со ссылкой на Actions при провале запуска,
исчерпании попыток доставки и ошибке сигнала мониторингу. Содержимое писем
не передаётся. Проверка доступна через `test_notification`.

Для обнаружения отсутствующих запусков настройте [Healthchecks.io](https://healthchecks.io/):
период **5 минут**, Grace Time **20 минут**, Ping URL — в `HEALTHCHECK_URL`.
Сигнал отправляется после успешной обычной проверки и сохранения состояния,
если очередь ошибок новых писем пуста. Ручная история сигнал не отправляет.
Без внешнего сервиса остановка расписания не обнаруживается; для независимых
уведомлений можно подключить email. Повторы самих уведомлений не гарантируются.

## Ограничения

- Исключения отправителей заданы в `EXCLUDED_SENDERS` в [mail2tg.py](mail2tg.py).
  Сравнивается точный адрес `From` без учёта регистра; фильтр действует и на историю.
- Скриншоты не загружают внешние ресурсы и не выполняют JavaScript.
  Встроенные CID-изображения сохраняются; оформление может отличаться от оригинала.
- HTML со встроенными изображениями ограничен 5 МиБ, область снимка —
  1200 × 18000 CSS-пикселями, результат — 10 кадрами до 2400 × 3600 пикселей.
  Более тяжёлый HTML отправляется без скриншота. Жёсткой квоты памяти браузера нет.

## Разработка и тесты

```bash
python -m pip install -r requirements.txt
python -m pip check
python -B -m unittest discover -s tests -v
```

Тесты работают без почты, Telegram и секретов. Для браузерной проверки нужны
Chrome и переменная `MAIL2TG_BROWSER_TESTS=1`; иначе этот тест пропускается.

CI запускается при изменении Python-кода, зависимостей или workflow, а также
вручную. Основные проверки выполняются перед пересылкой; при провале отправка
не начинается. Отдельный workflow проверяет скриншоты настоящим Chrome.
Прямые зависимости закреплены; транзитивные зависимости и браузер — нет.

Планы и оставшиеся задачи: [BACKLOG.md](BACKLOG.md).
