# mail2tg

Пересылка писем из почтового ящика в Telegram-канал.

Скрипт `mail2tg.py` по расписанию в GitHub Actions проверяет ящик по IMAP (только чтение) и публикует новые письма в канал через Telegram-бота: тему, отправителя, дату, текст и вложения.

Настройки и пароли хранятся в секретах GitHub Actions.

Письма от `info@360.yandex.ru`, `noreply@id.yandex.ru`, `hello@360.yandex.ru`
и `mailer-daemon@yandex.ru` исключены из пересылки,
включая вложения и скриншоты. Сравнивается точный адрес отправителя в `From`
без учёта регистра; имя отправителя не влияет на проверку. Исключения действуют
и при пересылке истории. Список можно изменить в `EXCLUDED_SENDERS` в `mail2tg.py`.
Пропущенные письма учитываются в сохранённой позиции, но остаются в почте без изменений.

## Пересылка истории

Обычный запуск с пустым `since` отправляет новые письма и обновляет `last_uid`.
Для cron-job.org всегда оставляйте `since` пустым.

Ручной запуск с датой `since` повторяет уже обработанные письма начиная с этого
дня. Он не меняет `last_uid`: новые, ещё не обработанные письма остаются для
обычного запуска. Верхняя граница истории фиксируется при выборе даты, поэтому
поступившие позже письма не добавляются в эту пересылку.

История отправляется порциями до `max_per_run` писем. Повторный ручной запуск
с той же датой продолжает со следующей порции; cron историю не продолжает.
Даты `2026-09-01` и `01.09.2026` считаются одинаковыми. После завершения запуск
с той же датой ничего не отправляет. Другая дата начинает новую пересылку истории.
Отдельный прогресс хранится в объекте `backfill` в `state.json`. Чтобы повторить
ту же историю с начала, нужно удалить этот объект из актуального состояния,
сохранив `uidvalidity` и `last_uid`, и отправить изменение в репозиторий.

При первом запуске или изменении IMAP `UIDVALIDITY` позиции инициализируются
заново. Если при этом задана дата, история пересылается до зафиксированной
текущей позиции; обычный запуск пропускает старые письма.

## Ошибки доставки и повторы

Ошибка загрузки или отправки письма сохраняется в `state.json` в объекте
`failed`: UID, число попыток и тип исключения, без содержимого письма.
Позиция просмотра продвигается, но неудачные письма остаются в отдельной очереди.
Каждый запуск повторяет часть очереди и обрабатывает новые письма в пределах
общего `max_per_run`. При лимите 1 новые письма имеют приоритет над повторами.
После пяти неудачных попыток автоматические повторы останавливаются;
запись остаётся для ручного разбора. Удалённое из почты письмо также останется
в очереди ошибок, если его больше невозможно загрузить.

Очередь `live` относится к новым письмам. Очереди `history:<дата>` относятся
к истории: их повторяют только ручные запуски с соответствующей датой `since`.
Смена даты не удаляет ошибки предыдущей истории. Cron с пустым `since`
не повторяет историю. При изменении `UIDVALIDITY` старые очереди сбрасываются,
поскольку их UID больше нельзя использовать для новой нумерации папки.

Чтобы повторить письмо после исчерпания попыток, запустите workflow вручную
с `retry_uids`, например `19,21`. Для ошибок истории также задайте её дату `since`.
Это сбрасывает счётчик только перечисленных ошибок выбранной очереди;
успешно обработанные UID заново не отправляются. В cron-job.org оставляйте
`retry_uids` пустым или не передавайте его, чтобы лимит не сбрасывался постоянно.

В конце запуска лог показывает число отправленных писем, ожидающих повтора
и требующих ручного повтора. Наличие ошибок отдельных писем пока не делает
workflow неуспешным: проверяйте эти счётчики. Ошибки открытия папки и поиска
останавливают запуск без продвижения позиции. Исключённые отправители
считаются обработанными и не попадают в очередь ошибок.

## Продолжение частичной отправки

Для неудачных писем объект `deliveries` в состоянии хранит ID первого сообщения,
число подтверждённых частей текста, индексы отправленных вложений и этап скриншота.
После сбоя повтор продолжает незавершённые этапы, привязывая их к первому сообщению.
Альбом считается отправленным после успешного ответа Telegram. Если альбом
отклонён и файлы отправляются по одному, каждый файл сохраняется отдельно.
Успешно завершённые записи удаляются вместе с обновлением позиции обработки.

Ошибка создания скриншота записывается в лог и не мешает доставке письма.
Ошибка отправки готового скриншота оставляет письмо в очереди повтора,
но подтверждённые текст и вложения повторно не отправляются.
При изменении текста подготовленных сообщений, исходного письма или канала
во время незавершённой доставки повтор останавливается с `RuntimeError`
(`DeliveryPlanChanged`), чтобы не смешивать этапы разных вариантов письма.
Такую ошибку нужно разобрать вручную: сброс счётчика попыток сам по себе
не сбрасывает прогресс.

Подтверждения записываются в локальное состояние сразу после ответа Telegram,
а в репозиторий — в конце запуска. Если push состояния не удался, workflow
пытается сохранить `state.json` как артефакт `mail2tg-state-<ID запуска>` на 7 дней.
Остановите внешнее расписание, скачайте артефакт из неудачного запуска,
сверьте его с актуальным состоянием и восстановите прогресс в репозитории,
прежде чем возобновлять запуски. Не заменяйте более новое состояние старой копией.
Создание артефакта тоже может завершиться ошибкой; это резервная копия,
а не замена успешному сохранению состояния.

Абсолютной гарантии отсутствия дублей нет: Telegram мог принять запрос,
ответ на который потерялся, или процесс мог завершиться до записи подтверждения.
При отмене задания, таймауте либо сбое сохранения удалённой копии возможна
потеря локального прогресса и повтор уже отправленных этапов.

Проверки без почты и Telegram: `python -B -m unittest discover -s tests -v`.

## Зависимости и автоматические тесты

Python-библиотеки закреплены в `requirements.txt`. Установка:
`python -m pip install -r requirements.txt`. Проверка совместимости установленных
пакетов: `python -m pip check`. Для обновления меняйте версии явно и проверяйте
установку, импорты библиотек и тесты перед публикацией.
Зависимости самих библиотек разрешает pip; этот файл не является полным lock-файлом.

Workflow «Тесты» запускается при push и pull request с изменениями Python-кода,
`requirements.txt` или workflow, а также вручную. Изменения только `state.json`
не запускают отдельный workflow тестов. Проверки используют Ubuntu 24.04
и Python 3.12, не получают секретов и не подключаются к почте или Telegram.
Проверяются установка зависимостей, синтаксис скриптов, импорты библиотек
и тесты из `tests/`. Отдельный шаг проверяет ограничения скриншотов настоящим
Chrome на искусственном HTML, без почты и Telegram: внешние ресурсы направлены
на локальный тестовый сервер и должны блокироваться.

Основной workflow также проверяет зависимости и запускает тесты до пересылки.
Если проверка не прошла, отправка писем не начинается; шаги сохранения состояния
и уведомления владельца выполняются по прежним правилам.
Проверки в Actions сами по себе не запрещают push или merge: обязательную
проверку для слияния можно отдельно включить в правилах защиты ветки.

Версия предустановленного Chrome в образе GitHub пока не закреплена.
Фиксация `playwright` закрепляет Python-библиотеку, а не этот браузер.

## Ограничения скриншотов

При создании скриншотов браузер блокирует внешние запросы, включая изображения,
CSS и iframe. JavaScript и service workers отключены. Встроенные в письмо
CID-изображения подставляются как `data:` и сохраняются; изображения с внешних
сайтов и внешний CSS могут отсутствовать, поэтому вид письма может отличаться
от почтового клиента. Текст письма, ссылки и вложения отправляются отдельно.

HTML вместе с подставленными изображениями ограничен 5 МиБ: более тяжёлое
письмо отправляется без скриншота, с записью причины в лог.
До захвата измеряется страница. Ширина ограничена 1200 CSS-пикселями,
высота — 18000; снимки создаются порциями по 1800, максимум 10 кадров.
С учётом масштаба 2 один кадр не превышает 2400 × 3600 пикселей.
Содержимое за этими границами на снимок не попадает. Предварительный снимок
всей неограниченной страницы больше не создаётся.
Это ограничивает входной HTML и размеры PNG, но не является жёсткой квотой
памяти браузера для произвольной сложной вёрстки.

Для локальной браузерной проверки установите зависимости и Chrome, задайте
`MAIL2TG_BROWSER_TESTS=1` и запустите тесты. Без этой переменной браузерный
тест пропускается; остальные проверки не требуют установленного браузера.

## Защита файла состояния

Перед чтением и записью проверяется структура позиции, истории, очередей ошибок
и прогресса доставки. Отсутствующий файл, повреждённый JSON, неверная кодировка
или некорректная структура останавливают запуск до подключения к почте.
Бот не заменяет такие данные пустым состоянием. Восстановите актуальную копию
из истории Git либо резервного артефакта, сохранив уже подтверждённый прогресс.

Запись выполняется во временный файл в той же папке: данные сбрасываются на диск,
затем файл атомарно заменяет `state.json`. Ошибка сохранения останавливает отправку,
а не попадает в очередь обычных ошибок писем. Атомарная замена защищает от
частично записанного JSON, но не заменяет резервное копирование и успешный push.

Для намеренного первого подключения нового ящика можно создать `state.json`
с содержимым `{}`. Это явный сброс: при обычном запуске бот запомнит текущую
позицию и пропустит накопившиеся письма. Не используйте его для исправления
ошибки чтения существующего состояния.

## Личные уведомления и контроль запусков

Добавьте GitHub Secret `TG_ADMIN_CHAT_ID` с ID личного чата владельца.
Сначала откройте бота в Telegram и нажмите Start. Используется существующий
`TG_TOKEN`; `TG_CHAT_ID` учебного канала не меняется.

Для проверки откройте Actions → «Почта → Telegram» → Run workflow и включите
«Только тест уведомления владельцу (без обработки почты)». Остальные поля
в этом режиме игнорируются. Выполняется отдельное задание с правами чтения:
оно отправляет тестовое сообщение и ссылку на запуск только владельцу,
не читает почту, не записывает состояние и не отправляет сигнал мониторингу.
При отсутствии секретов или ошибке отправки тест завершается ошибкой.
Если ID владельца совпадает с ID учебного канала, отправка теста блокируется.
В cron-job.org не передавайте `test_notification` либо оставляйте `false`.

После завершения workflow скрипт `monitoring.py` отправляет владельцу:

- Уведомление о неуспешном или отменённом запуске, включая ошибку сохранения состояния.
- Уведомление о письмах, которые в этом запуске исчерпали пять попыток доставки.
- Уведомление об ошибке отправки сигнала внешнему мониторингу, если он настроен.

Сообщения содержат ссылку на запуск Actions, а для ошибок доставки — UID.
Темы, отправители и содержимое писем не передаются. Для сравнения ошибок
используется копия состояния до запуска в каталоге runner. Одна и та же
исчерпанная ошибка не уведомляет владельца на каждом запуске.
Если само уведомление не доставлено, шаг завершается ошибкой; отдельная очередь
повторов уведомлений пока отсутствует. При отсутствии секрета владельца
уведомления отключены, о чём выводится запись в лог.

Чтобы обнаруживать отсутствие запусков, создайте независимую проверку, например
на [Healthchecks.io](https://healthchecks.io/), с периодом 5 минут и Grace Time
20 минут. Подключите в ней уведомления на email или Telegram. Обычный Ping URL
вида `https://hc-ping.com/<uuid>` сохраните в GitHub Secrets как `HEALTHCHECK_URL`.
Это секретный URL: не добавляйте его в код и публичные сообщения.

Сигнал успеха отправляется после успешного workflow и сохранения состояния,
если запуск был с пустым `since` и в очереди новых писем нет ошибок.
Пустой ящик также считается успешной проверкой. Ручная история не отправляет
этот сигнал. При периоде 5 минут и Grace Time 20 минут предупреждение ожидается
примерно через 25 минут после последнего сигнала. После настройки дождитесь
первого сигнала и проверьте уведомления, временно приостановив расписание.
Протокол описан в [документации Healthchecks.io](https://healthchecks.io/docs/http_api/).

Без `HEALTHCHECK_URL` работают только уведомления при выполнении workflow.
Если GitHub не создал запуск или runner завершился до последнего шага,
код уведомления не выполнится. При полном отказе Telegram уведомления тем же
ботом также недоступны: для внешнего контроля полезно подключить email.
