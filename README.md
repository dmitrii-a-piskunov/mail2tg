# mail2tg

Пересылка писем из почтового ящика в Telegram-канал.

Скрипт `mail2tg.py` по расписанию в GitHub Actions проверяет ящик по IMAP (только чтение) и публикует новые письма в канал через Telegram-бота: тему, отправителя, дату, текст и вложения.

Настройки и пароли хранятся в секретах GitHub Actions.

Письма от `info@360.yandex.ru`, `noreply@id.yandex.ru`, `hello@360.yandex.ru`
и `mailer-daemon@yandex.ru` исключены из пересылки,
включая вложения и скриншоты. Сравнивается точный адрес отправителя в `From`
без учёта регистра; имя отправителя не влияет на проверку. Исключения действуют
и при пересылке истории. Список можно изменить в `EXCLUDED_SENDERS` в `mail2tg.py`.
Пропущенные письма учитываются в сохранённой позиции, но остаются в почте без изменений.

## Пересылка истории

Обычный запуск с пустым `since` отправляет новые письма и обновляет `last_uid`.
Для cron-job.org всегда оставляйте `since` пустым.

Ручной запуск с датой `since` повторяет уже обработанные письма начиная с этого
дня. Он не меняет `last_uid`: новые, ещё не обработанные письма остаются для
обычного запуска. Верхняя граница истории фиксируется при выборе даты, поэтому
поступившие позже письма не добавляются в эту пересылку.

История отправляется порциями до `max_per_run` писем. Повторный ручной запуск
с той же датой продолжает со следующей порции; cron историю не продолжает.
Даты `2026-09-01` и `01.09.2026` считаются одинаковыми. После завершения запуск
с той же датой ничего не отправляет. Другая дата начинает новую пересылку истории.
Отдельный прогресс хранится в объекте `backfill` в `state.json`. Чтобы повторить
ту же историю с начала, нужно удалить этот объект из актуального состояния,
сохранив `uidvalidity` и `last_uid`, и отправить изменение в репозиторий.

При первом запуске или изменении IMAP `UIDVALIDITY` позиции инициализируются
заново. Если при этом задана дата, история пересылается до зафиксированной
текущей позиции; обычный запуск пропускает старые письма.

## Ошибки доставки и повторы

Ошибка загрузки или отправки письма сохраняется в `state.json` в объекте
`failed`: UID, число попыток и тип исключения, без содержимого письма.
Позиция просмотра продвигается, но неудачные письма остаются в отдельной очереди.
Каждый запуск повторяет часть очереди и обрабатывает новые письма в пределах
общего `max_per_run`. При лимите 1 новые письма имеют приоритет над повторами.
После пяти неудачных попыток автоматические повторы останавливаются;
запись остаётся для ручного разбора. Удалённое из почты письмо также останется
в очереди ошибок, если его больше невозможно загрузить.

Очередь `live` относится к новым письмам. Очереди `history:<дата>` относятся
к истории: их повторяют только ручные запуски с соответствующей датой `since`.
Смена даты не удаляет ошибки предыдущей истории. Cron с пустым `since`
не повторяет историю. При изменении `UIDVALIDITY` старые очереди сбрасываются,
поскольку их UID больше нельзя использовать для новой нумерации папки.

Чтобы повторить письмо после исчерпания попыток, запустите workflow вручную
с `retry_uids`, например `19,21`. Для ошибок истории также задайте её дату `since`.
Это сбрасывает счётчик только перечисленных ошибок выбранной очереди;
успешно обработанные UID заново не отправляются. В cron-job.org оставляйте
`retry_uids` пустым или не передавайте его, чтобы лимит не сбрасывался постоянно.

В конце запуска лог показывает число отправленных писем, ожидающих повтора
и требующих ручного повтора. Наличие ошибок отдельных писем пока не делает
workflow неуспешным: проверяйте эти счётчики. Ошибки открытия папки и поиска
останавливают запуск без продвижения позиции. Исключённые отправители
считаются обработанными и не попадают в очередь ошибок.

Повтор пока выполняется для письма целиком: если часть уже отправилась до
сбоя, она может прийти повторно. Сохранение этапов отправки — следующий пункт
backlog. Успешное сохранение состояния в GitHub остаётся необходимым для
восстановления прогресса между запусками.

Проверки без почты и Telegram: `python -B -m unittest discover -s tests -v`.
