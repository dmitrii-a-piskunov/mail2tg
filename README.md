# mail2tg

**Почта учебной группы → Telegram-канал.**

Бот проверяет Яндекс Почту по IMAP и публикует тему, отправителя, дату, текст,
вложения и скриншоты. Письма остаются в ящике и не помечаются прочитанными.
Код выполняется в GitHub Actions; запуск каждые пять минут настроен через
cron-job.org. Встроенное расписание GitHub сохранено, но может задерживаться.

## Настройка

Добавьте секреты в **Settings → Secrets and variables → Actions**:

| Секрет | Назначение |
| --- | --- |
| `IMAP_USER` | Адрес почтового ящика |
| `IMAP_PASSWORD` | Пароль приложения Яндекса |
| `TG_TOKEN` | Токен Telegram-бота |
| `TG_CHAT_ID` | ID или `@username` учебного канала |
| `TG_ADMIN_CHAT_ID` | Необязательно: ID личного чата владельца для уведомлений |
| `HEALTHCHECK_URL` | Необязательно: Ping URL внешнего мониторинга |

Дайте боту право публикации в канале. Для личных уведомлений откройте бота
и нажмите **Start**.

По умолчанию: `imap.yandex.ru`, папка `INBOX`, часовой пояс `Europe/Samara`,
до 20 писем за запуск, скриншоты всех HTML-писем. Настройки задаются в коде
и окружении [workflow](.github/workflows/mail2tg.yml); одноимённые секреты
без подключения к workflow их не переопределяют.

**Первый обычный запуск запоминает позицию и пропускает старые письма.**

## Запуск

**Actions → Почта → Telegram → Run workflow**:

| Параметр | Действие |
| --- | --- |
| `since` | Пусто — новые письма. `2026-09-01` или `01.09.2026` — повтор обработанной истории |
| `max_per_run` | Общий лимит писем и повторов за запуск; по умолчанию 20 |
| `retry_uids` | UID неудачных писем через запятую: сбросить лимит попыток, например `19,21` |
| `test_notification` | Только тест личного уведомления, без почты и изменения состояния |

### cron-job.org

Создайте задачу каждые пять минут с методом **POST**:

```text
https://api.github.com/repos/dmitrii-a-piskunov/mail2tg/actions/workflows/mail2tg.yml/dispatches
```

Заголовки:

```text
Authorization: Bearer <GITHUB_TOKEN>
Accept: application/vnd.github+json
Content-Type: application/json
X-GitHub-Api-Version: 2026-03-10
```

Тело запроса:

```json
{
  "ref": "main",
  "inputs": {
    "since": "",
    "max_per_run": "20"
  }
}
```

Нужен отдельный fine-grained GitHub-токен с доступом к этому репозиторию
и правом **Actions: Read and write**. Храните его в cron-job.org и заменяйте
после истечения срока. В автоматической задаче `since` и `retry_uids`
должны быть пустыми, `test_notification` — выключен.

### История

Дата в `since` повторяет уже обработанные письма, **не меняя позицию cron**.
Граница истории фиксируется при выборе даты; новые письма заберёт обычный запуск.

- Та же дата продолжает следующую порцию; после завершения ничего не отправляет.
- Другая дата начинает новую пересылку. Cron историю не продолжает.
- Для повтора с начала удалите `backfill` из актуального `state.json`, сохранив
  остальные данные, и сделайте push. Сначала разберите ошибки частичной доставки.

## Доставка и восстановление

Подтверждённые части текста, вложения и ID первого сообщения сохраняются.
После сбоя бот продолжает незавершённые этапы. Неудачные письма хранятся
в отдельных очередях для новых писем и каждой даты истории.

**После пяти неудачных попыток нужен ручной повтор:** укажите UID в `retry_uids`.
Для истории также задайте её `since`. Успешные письма повторно не отправляются.
При лимите 1 новые письма имеют приоритет над повторами.

Счётчики и ошибки видны в логах Actions. Ошибка отдельного письма не делает
весь workflow неуспешным. Ошибка открытия папки, поиска или сохранения состояния
останавливает обработку; ошибка создания скриншота не мешает отправке письма.

| Поле `state.json` | Содержимое |
| --- | --- |
| `uidvalidity`, `last_uid` | Нумерация папки и позиция обычной обработки |
| `backfill` | Позиция и граница истории |
| `failed` | Неудачные UID, число попыток и тип ошибки |
| `deliveries` | Прогресс частичной доставки |

Состояние проверяется и записывается атомарно. Отсутствующий или повреждённый
файл останавливает запуск. При смене IMAP `UIDVALIDITY` позиции и очереди
инициализируются заново. Пустой объект `{}` — намеренный сброс с пропуском
старых писем при обычном запуске; не используйте его для восстановления.

**Если push состояния не удался:** приостановите расписание, скачайте артефакт
`mail2tg-state-<ID запуска>` из Actions, сверьте с актуальным состоянием
и восстановите прогресс перед возобновлением работы. Артефакт хранится 7 дней,
если его загрузка удалась. Не заменяйте новое состояние старой копией.

Дубли возможны при потере ответа Telegram или состояния до успешного push.
Изменение письма, канала или подготовленного текста во время частичной доставки
блокирует повтор (`DeliveryPlanChanged`) и требует ручного разбора.

## Уведомления

Владелец получает ссылку на запуск при провале workflow, исчерпании попыток
доставки и ошибке сигнала мониторингу. Содержимое писем не передаётся;
одна и та же исчерпанная ошибка не уведомляет при каждом запуске.
Отдельной очереди повторов самих уведомлений нет.

**Проверка:** включите `test_notification` в ручном запуске. Остальные поля
игнорируются. Без секретов или при ошибке отправки тест завершается ошибкой;
совпадение ID владельца с ID канала блокирует тест.

Для обнаружения отсутствующих запусков подключите [Healthchecks.io](https://healthchecks.io/):
период **5 минут**, Grace Time **20 минут**, Ping URL — в `HEALTHCHECK_URL`.
Настройте уведомления сервиса и дождитесь первого сигнала. Он отправляется
после успешной обычной проверки и сохранения состояния, если очередь ошибок
новых писем пуста. Пустой ящик считается успехом; ручная история — нет.

Без внешнего мониторинга незапущенный бот не сможет сообщить об остановке.
На случай отказа Telegram подключите email в независимом сервисе.

## Фильтры и скриншоты

Исключения заданы в `EXCLUDED_SENDERS` в [mail2tg.py](mail2tg.py):

```text
info@360.yandex.ru
noreply@id.yandex.ru
hello@360.yandex.ru
mailer-daemon@yandex.ru
```

Проверяется точный адрес `From` без учёта регистра. Исключения действуют
для новых писем и истории, включая вложения и скриншоты.

В скриншотах заблокированы внешние изображения, CSS, iframe, JavaScript
и service workers. Встроенные CID-картинки сохраняются; вид письма может
отличаться от почтового клиента.

| Ограничение | Значение |
| --- | --- |
| HTML со встроенными изображениями | 5 МиБ; более тяжёлые письма — без скриншота |
| Область страницы | До 1200 × 18000 CSS-пикселей |
| Снимки | До 10 кадров, каждый до 2400 × 3600 пикселей |

Содержимое за границами снимка доступно в почте. Жёсткой квоты памяти браузера нет.

## Разработка

Окружение CI: **Python 3.12 · Ubuntu 24.04**.

```bash
python -m pip install -r requirements.txt
python -m pip check
python -B -m unittest discover -s tests -v
```

Тесты не используют почту, Telegram и секреты. Браузерный тест требует Chrome
и `MAIL2TG_BROWSER_TESTS=1`; без этой переменной он пропускается.

Workflow «Тесты» запускается при изменении Python-кода, зависимостей или workflow,
а также вручную. Проверки выполняются и перед пересылкой: при провале отправка
не начинается. CI отдельно проверяет ограничения скриншотов настоящим Chrome.

Прямые зависимости закреплены в [requirements.txt](requirements.txt);
транзитивные зависимости и предустановленный Chrome не зафиксированы.
Планы развития — в [BACKLOG.md](BACKLOG.md).
